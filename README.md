# Фотомозаика

Загружаете фотографию → кадрируете → выбираете размер сетки и палитру → получаете
мозаику, где **цвет каждой ячейки — среднее по всем пикселям её области исходного
снимка** (не центральный пиксель), заменённое **ближайшим цветом физической
палитры** по перцептивному расстоянию в CIE L\*a\*b\*. Всё считается в браузере,
файл никуда не отправляется.

Результат рисуется в один `<canvas>`, а не тысячами DOM-элементов.

---

## Запуск

```bash
npm install
npm run dev          # http://localhost:3000
```

Прод-сборка:

```bash
npm run build && npm start
```

### Проверка без установки зависимостей

`standalone/index.html` — автономная страница с тем же ядром. Откройте файл
двойным кликом: загрузка, кадрирование, генерация, сравнение и скачивание PNG
работают без сборки и без сети.

### Мобильная версия

Та же автономная страница рассчитана на телефон: её можно открыть по ссылке
(опубликованная страница) или как файл. Что в ней сделано специально для
телефонов:

- **Кадрирование пальцами** — один палец двигает кадр, два масштабируют
  (щипок), колесо и ползунок остаются для десктопа.
- **Расчёт в фоновом потоке** — варианты считаются в Web Worker, интерфейс не
  замирает, «Отменить» прерывает расчёт. Если воркер запустить нельзя
  (политика безопасности страницы, старый браузер), тот же код считает на
  главном потоке.
- **Память под canvas** — на телефонах и планшетах превью вариантов рисуются
  в 1024 px, а не 2048 (одиннадцать полноразмерных превью исчерпывают лимит
  canvas в мобильном Safari, и картинки гаснут). Полноразмерный PNG
  дорисовывается из сетки при скачивании — данные те же.
- **PNG на экране** — на телефоне «Скачать PNG» показывает картинку, её
  сохраняют долгим нажатием; кнопка «Сохранить файлом» отдаёт тот же файл.
- **Открытие снимка** — `<img>` через blob-URL (браузер сам применяет
  EXIF-поворот), запасные пути через data-URL и `createImageBitmap`.

Версия для публикации собирается из той же страницы:

```bash
npm run build:artifact      # standalone/index.html + standalone/artifact.html
```

`artifact.html` — та же страница без внешнего каркаса документа (хостинг
добавляет свой) и с подключёнными шрифтами IBM Plex.

Проверка в эмуляции телефона (Chromium 390×844, touch, dpr 3 — жесты,
отмена, размеры превью, память canvas, PNG и PDF):

```bash
PHOTO=path/to/photo.jpg npm run check:mobile
```

**Что покрыто юнит-тестами** (`tests/gridAverage.test.mjs`):

- ячейка получает среднее, а не центральный пиксель (3×3 с чёрным центром на
  белом даёт `#E3E3E3`, а не `#000000`);
- квадранты попадают в свои ячейки, порядок ячеек row-major;
- границы ячеек покрывают изображение без дыр и пересечений, в том числе когда
  размер не кратен сетке (37×11 → 5×3);
- градиент усредняется по своей полосе;
- полупрозрачность композитится на подложку;
- линейное усреднение отличается от sRGB;
- формат `hex` и валидация некорректного ввода;
- 1600×1600 → 64×64 укладывается в сотню миллисекунд.

**Что покрыто тестами цветовой системы** (`tests/color.test.mjs`):

- `rgbToLab` совпадает со справочными значениями (красный → `L 53.2408, a 80.0925,
  b 67.2032`), белый переводится в точку белого D65, обратное преобразование
  возвращает исходный RGB для 34 цветов;
- `deltaE2000` проверена на 15 контрольных парах из статьи Sharma, Wu, Dalal
  (2005) с точностью до 0.0001 — это тот самый набор, на котором ловятся
  типичные ошибки в формуле (переход через 0°/360° по тону, член `RT`);
- ΔE76 и ΔE94 — свойства, симметрия, нулевое расстояние;
- пример из задачи: `RGB(127, 84, 71)` → **Brown**;
- каждый цвет палитры находит сам себя с расстоянием 0;
- таблица из 26 разных цветов → ожидаемые названия деталей;
- поиск действительно возвращает минимум: результат сверяется с полным перебором
  на 150 случайных цветах для каждой из трёх метрик;
- сопоставление сетки: координаты сохраняются, исходные средние цвета не портятся,
  суммы в статистике сходятся, 9 216 ячеек обрабатываются за ~70 мс.

**Что покрыто тестами ограничений** (`tests/pieceLimit.test.mjs`):

- Sobel находит границу и молчит на заливке; карты по ячейкам дают высокий edge
  на контуре квадрата и ноль внутри него;
- `calculateReplacementCost` раскладывается ровно на три слагаемых, замена на
  контуре дороже, чем в заливке, веса переопределяются;
- **палитра из 3 цветов + искусственный лимит**: после оптимизации у всех цветов
  `required ≤ available`, ни одна ячейка не потерялась, статусы верные;
- переносятся именно самые дешёвые ячейки, а не первые попавшиеся;
- при равной цвето́вой цене контурные ячейки сохраняют цвет, а уступают ровные;
- если лимиты уже соблюдены — ноль переназначений; если деталей физически не
  хватает — `feasible: false` вместо бессмысленной перекраски;
- исходное сопоставление не мутируется, результат воспроизводим;
- 64×64, 96×96 и 128×128 укладываются в бюджет времени.

**Что покрыто тестами портретного режима** (`tests/face.test.mjs`): см. раздел
«Портреты» ниже — 20 проверок от правил кожи до измеримого эффекта карты весов.

**Что покрыто тестами вариантов** (`tests/variants.test.mjs`): идеальное
совпадение даёт 1.0 по всем составляющим; повторный расчёт даёт тот же результат;
дальний цвет обнуляет colorSimilarity; стёртый контраст обнуляет
edgePreservation; испорченные глаза роняют facePreservation, а такая же ошибка на

палитры всегда хватает на сетку; четыре пресета различаются каждым из
перечисленных параметров.

**Что покрыто сквозным тестом** (`tests/flow.browser.mjs`): открыть страницу →
загрузить файл → изменить масштаб и вписать кадр → выбрать 64×64 → создать
мозаику → сверить цвета **прямо с пикселями canvas** → подвигать шторку и зум →

консоль чистая. Отдельно проверяется палитра: все 4 096 ячеек оказываются цветами
деталей, углы совпадают с ожидаемыми `#C4281B / #58AB41 / #0055BF / #F5CD2F`,
средние цвета сохранены отдельно в `averageGrid`, таблица статистики и легенда
показывают те же числа, а итог равен числу ячеек. Отдельно — четыре варианта:
все с соблюдённым запасом, с разными настройками и разными пикселями, оценки
воспроизводимы, а выбранный вариант действительно становится главным
результатом. И запас деталей:
после включения лимитов ни один цвет не превышает `availableQuantity`, красный
получает статус `corrected`, сумма Required равна числу ячеек.

## Данные

`computeAverageGrid` возвращает ячейки строго в таком виде:

```json
[
  {
    "x": 0,
    "y": 0,
    "rgb": [120, 80, 60],
    "hex": "#78503C"
  }
]
```

`x` и `y` — координаты **в сетке** (0..cols-1 и 0..rows-1), порядок row-major.
Кнопка «Сетка в JSON» выгружает этот массив целиком.

## Как считается цвет

1. Кадр из кроппера рисуется в рабочий canvas. Его сторона всегда кратна числу
   ячеек, поэтому на каждую приходится ровно `k × k` пикселей — усреднение без
   краевого перекоса. Ограничение — `MAX_SAMPLE_SIZE` в `config/mosaic.ts`.
2. `computeAverageGrid` идёт по ячейкам и суммирует **все** пиксели области.
   Границы берутся как `floor(i * size / count)`, поэтому области не пересекаются
   и покрывают изображение целиком.
3. Полупрозрачные пиксели композитятся на подложку.
4. Режим `linear` переводит цвета в линейный свет перед усреднением — контрастные
   переходы получаются светлее и ближе к физике; `srgb` считает по байтам.
5. `renderMosaicToCanvas` рисует ячейки прямоугольниками или кругами; сторона
   ячейки подбирается так, чтобы итог был около `TARGET_OUTPUT_SIZE`.

## Палитра деталей

Все цвета лежат в `src/config/palettes.json`. Формат:

```json
{
  "basic": [
    {
      "id": "black",
      "name": "Black",
      "hex": "#111111",
      "rgb": [17, 17, 17],
      "availableQuantity": 500
    }
  ]
}
```

Можно менять **название, HEX, RGB и количество** — код перекомпилировать не нужно,
Next подхватит файл на лету. Ключ верхнего уровня — id палитры; чтобы добавить
свою, допишите ещё один ключ с массивом цветов, и она сама появится в
переключателе. Демонстрационная палитра `basic` — 12 цветов, `grayscale` — пример
второй палитры из 4 оттенков.

При загрузке файл проверяется (`parsePalettes`): непустые `id` и `name`, корректный
`hex`, уникальность `id`, `availableQuantity ≥ 0`. Если `rgb` разошёлся с `hex`,
побеждает `hex`, а расхождение попадает в предупреждение в консоли — опечатка не
превращается в тихо неверный цвет. Подпись палитры в интерфейсе задаётся в
`PALETTE_LABELS` (`src/config/paletteData.ts`), по умолчанию берётся id.

Ни один цвет не зашит в алгоритмы: `findNearestPaletteColor` и `mapGridToPalette`
всегда получают палитру аргументом.

### Как подбирается цвет

1. Средние цвета ячеек считает `gridAverage` — палитра на этот шаг не влияет.
2. `rgbToLab` переводит цвет ячейки и каждый цвет палитры в CIE L\*a\*b\* (D65).
   Lab устроен так, что расстояние в нём примерно соответствует разнице, которую
   видит глаз — в отличие от RGB, где «зелёный ближе к синему, чем к другому
   зелёному» встречается сплошь и рядом.
3. `deltaE2000` (по умолчанию) считает перцептивное расстояние. Доступны также
   `cie94` и `cie76` — метрика переключается в интерфейсе и передаётся параметром
   `distanceMetric`.
4. `mapGridToPalette` выбирает минимум по палитре для каждой ячейки. Повторяющиеся
   цвета кэшируются, поэтому 9 216 ячеек × 12 цветов считаются за ~70 мс.
5. Результат: новая сетка в цветах деталей, массив индексов `assignments`,
   статистика `usage` и средняя/максимальная ошибка ΔE. Исходные средние цвета
   остаются в `result.averageGrid`.

Пример:

```ts
findNearestPaletteColor([127, 84, 71], getPalette('basic'));
// → { color: { id: 'brown', name: 'Brown', hex: '#7C503A', … }, distance: 4.09 }
```

## Ограниченный запас деталей

После сопоставления с палитрой какого-то цвета почти всегда нужно больше, чем
есть: например, красного требуется 932 детали при запасе 400. Оптимизатор
(`src/algorithms/optimization/pieceLimit.ts`) забирает лишние ячейки у
переполненных цветов и раздаёт их тем, у кого запас остался.

Как это работает:

1. первичный palette mapping (ближайший цвет, лимиты не учитываются);
2. подсчёт количества каждого цвета;
3. поиск превышений: `required > availableQuantity`;
4. для каждой ячейки переполненного цвета считается цена лучшей доступной
   альтернативы;
5. кандидаты складываются в кучу минимумов и разбираются от самых дешёвых:
   переносятся именно те ячейки, где замена меньше всего заметна;
6. шаги повторяются, пока остаются переполненные цвета.

Полного перебора нет. Если у выбранного цвета к моменту переноса кончился запас,
кандидат пересчитывается и возвращается в кучу — ленивая переоценка вместо
повторного полного прохода. Расстояния «цвет ↔ цвет» считаются один раз, а
«ячейка ↔ цвет» — лениво, только для тех ячеек, которых оптимизация коснулась.

### Цена замены

`calculateReplacementCost()` (`optimization/costFunction.ts`):

```
cost = colorDistance + structuralPenalty + edgePenalty

colorDistance     = ΔE(истинный цвет ячейки, кандидат)
structuralPenalty = w.structure × детальность × colorDistance
                  + w.cohesion  × (1 − граница) × ΔE(кандидат, соседи)
edgePenalty       = w.edge      × граница × ΔE(текущий цвет, кандидат)
```

Все слагаемые в единицах ΔE, поэтому складываются напрямую. Веса
(`DEFAULT_COST_WEIGHTS`) настраиваются параметром `costWeights` и ничего не знают
об оптимизаторе.

Смысл: замена внутри ровной заливки почти бесплатна, а на контуре глаза, рта или
границе объекта — дорога, поэтому такие ячейки уступают свои детали последними.

### Границы

`src/algorithms/image/edges.ts` считает по пикселям источника две карты в
разрешении сетки:

- **edge** — оператор Собеля по яркости (Rec. 709) с предварительным сглаживанием
  3×3 и подавлением немаксимумов вдоль градиента (первый шаг Canny), чтобы контур
  был тонким. Порогов с гистерезисом нет намеренно: оптимизатору нужна
  непрерывная величина, а не бинарная маска;
- **structure** — среднеквадратичный разброс яркости внутри ячейки: текстура,
  мелкие детали, ресницы, блики.

Обе карты нормируются по 98-му перцентилю, чтобы одиночный выброс не сжимал шкалу.
Если пикселей под рукой нет, `computeGridCellMaps` посчитает то же самое по
готовой сетке.

### Что показывается

Таблица получает колонки **Required / Available / Status**:

```
Red      required 400 / available 400  — corrected  (было 932)
Black    required 500 / available 500  — ok         (было 417)
Green    required  10 / available 350  — ok
```

`corrected` — цвет выходил за лимит и был приведён к нему, `ok` — уложился сам,
`over` — не удалось (бывает только когда деталей физически не хватает).

### Когда деталей не хватает в принципе

Если суммарный запас меньше числа ячеек, гарантировать ограничения невозможно.
Тогда оптимизатор ничего не перекрашивает, возвращает `feasible: false`, и
интерфейс прямо говорит, сколько деталей нужно. В демо-палитре запас (9 800 у `basic`, 11 100 у
`portrait`) примерно вдвое больше сетки 64×64 — ограничения срабатывают на
доминирующих цветах, но картинка не рассыпается.

Отключить учёт запасов можно кнопкой в интерфейсе или параметром
`enforcePieceLimits: false`.

(дефицит почти у всех):

| --- | --- | --- | --- | --- | --- | --- |

| 96×96 | 9 216 | 44 мс | 3 мс | 55 мс | **102 мс** | 3 757 |
| 128×128 | 16 384 | 56 мс | 17 мс | 118 мс | **191 мс** | 6 726 |

## Портреты: лицо, области и режимы

Цель этапа — чтобы человек оставался узнаваемым после превращения в сетку.
Никакой генеративной модели: только computer vision, и ни один пиксель не
дорисовывается.

### Поиск лица

`src/algorithms/face/faceDetection.ts` работает классической связкой:

1. изображение уменьшается до ~192 px по длинной стороне;
2. каждый пиксель проверяется правилами кожи — RGB-условия плюс коридор по Cb/Cr
   (Kovac, Chai-Ngan);
3. маска чистится морфологией: открытие убирает крапины, закрытие латает дыры;
4. связные компоненты (8-связность, без рекурсии) отбираются по площади,
   плотности заливки и пропорциям;
5. уверенность считается по близости пропорций к лицу и плотности пятна.

Если лицо не найдено, `faces` пуст, карта весов остаётся ровной и генерация идёт
обычным способом — никаких особых веток в конвейере.

**Обрезанные кадром лица.** В квадратном кропе портрет почти всегда упирается
в верх и низ: овал превращается в прямоугольник, и оценка по пропорциям его
отвергала. Такие находки распознаются по касанию края и оцениваются иначе —
по коридору пропорций, заполненности и размеру. Плюс перекрывающиеся пятна
кожи склеиваются: прядь волос поперёк лица больше не даёт «двоих в кадре».

На бенчмарке из 18 реальных фотографий это подняло долю найденных лиц с
**11/18 до 17/18** для квадратных наборов; разрыв между форматами кадра 1:1 и
2:3 исчез. Отключается флагами `edgeTolerant` и `mergeOverlapping`.

**MediaPipe или OpenCV можно подключить одной строкой** — детектор параметризован:

```ts
detectFaces(image, { detector: myMediaPipeDetector });
```

Встроенная эвристика работает офлайн и без весов моделей, но она проще
свёрточного детектора: профили, сильные тени и необычный цвет фона она пропустит.

### Области лица

`faceRegions.ts` разбирает найденный прямоугольник:

- **глаза** — две самые тёмные впадины в верхней половине; принимаются, только
  если заметно темнее окружающей кожи и лежат на одной высоте;
- **рот** — самая «красная» строка в нижней трети (Cr минус доля яркости);
- **волосы** — тёмная не-кожа над лицом;
- **овал и контур** — эллипс по рамке лица и кольцо вокруг него.

Ничего не найдено — поле остаётся пустым, вес просто не назначается.

### Карта весов

`optimization/weightMap.ts` переводит области в важность ячеек. Значения — из
`config/quality.ts`:

| область | вес |
| --- | --- |
| обычная | 1 |
| лицо | 1.5 |
| волосы | 1.6 |
| рот | 2.0 |
| контур лица | 2.0 |
| границы (Sobel) | 2.0 |
| глаза | 2.5 |

Вес умножает всю стоимость замены в `calculateReplacementCost`, поэтому при
дефиците деталей ячейку глаза сдвинуть в 2.5 раза дороже, чем такую же ячейку
фона. У границ вес растёт плавно вместе с силой градиента, а общий потолок —
`MAX_REGION_WEIGHT`.

Измеримый эффект (`npm run test:face`): при жёстком дефиците деталей с картой
весов портится **33.9%** важных ячеек (глаза, рот, контур) против **50.2%** без
неё.

### Режимы

Четыре режима меняют параметры алгоритма, а не CSS:

| режим | поиск лица | предобработка | усреднение | метрика | ячейка |
| --- | --- | --- | --- | --- | --- |
| **Standard** | нет | — | sRGB | ΔE00 | квадрат |
| **Portrait** | да | резкость 0.45, контраст 1.08 | sRGB | ΔE00 | квадрат |
| **High Contrast** | да | autoLevels, контраст 1.55 | линейное | ΔE00 | квадрат |
| **Artistic** | нет | насыщенность 1.3 | линейное | ΔE94 | круг, зазор 0.16 |

Плюс у каждого свои веса в функции стоимости: Portrait поднимает `edge` до 2.2 и
усиливает глаза, High Contrast — до 2.6, Artistic наоборот повышает связность
соседей, чтобы получались крупные плоские пятна.

Предобработка (`image/preprocess.ts`) меняет **пиксели до усреднения**: сначала
растягивание гистограммы, потом контраст и насыщенность, потом нерезкая маска.
Поэтому меняется сам результат — какие детали доживут до сетки и в какие цвета
палитры они попадут.

### A/B-превью

Кнопка «Сравнить режимы» строит четыре плитки на одном кадре: Original,
Standard, Portrait, High Contrast. Каждая — настоящая генерация со своими
параметрами; в браузерном тесте проверяется, что все четыре различаются
пиксельно.

### Портретная палитра

В `palettes.json` добавлена палитра `portrait` из 14 цветов с четырьмя тонами
кожи, румянцем и тёмными волосами. На палитре `basic` лицо уезжает в оранжевый —
не потому что алгоритм плох, а потому что телесного цвета в ней просто нет. Это
и есть смысл конфигурируемых палитр.

### На чём проверено

Тесты гоняются на синтетических изображениях (в офлайне настоящих фотографий
взять негде), зато полностью управляемых — известно, где нарисованы глаза и рот:

- портрет одного человека — лицо найдено, центр совпадает с нарисованным;
- двое в кадре — найдены оба;
- ребёнок (голова круглее и меньше) — найдено, глаза и рот на месте;
- животное (вытянутая морда) — отвергнуто по пропорциям;
- пейзаж с песчаной полосой — лиц нет, карта весов ровная;
- пустой белый кадр — детектор не падает.

Отдельно в браузере: портрет → лицо, два глаза, рот, волосы, вес 2.5 в ячейках
глаз; пейзаж → лиц нет и мозаика всё равно строится.

Честная оговорка: на настоящих фотографиях эвристика по коже будет ошибаться
чаще, чем свёрточный детектор. Архитектура к этому готова — интерфейс
`FaceDetector` подменяется без изменений в остальном конвейере.

## Варианты одной фотографии

Один запуск — четыре варианта. Отличаются они параметрами алгоритма, а не
случайным шумом: при одинаковом входе результат и оценки всегда одни и те же.

| вариант | палитра | цветов | контраст | насыщ. | сглаж. | вес цвета | вес границ | метрика |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **A** Точный цвет | вся | все | 1.0 | 1.0 | 0 | 1.3 | 1.2 | ΔE00 |
| **B** Портрет | вся | все | 1.08 | 0.96 | 0 | 1.0 | 2.4 | ΔE00 |
| **C** Контрастный | вся | все | 1.55 + autoLevels | 1.12 | 0 | 1.15 | 2.8 | ΔE00 |
| **D** Простая сборка | урезанная | 8 | 1.1 | 1.2 | 0.35 | 0.85 | 0.9 | ΔE94 |

Плюс у каждого свой режим (`standard`, `portrait`, `highContrast`, `artistic`),
своё пространство усреднения и своя форма ячейки. Пресеты лежат в
`src/config/variants.ts`.

Каждый вариант — объект:

```ts
{
  id: 'B',
  name: 'Портрет',
  settings,      // все параметры алгоритма
  mosaic,        // полный MosaicResult
  statistics,    // деталей, цветов, использование, требования, переназначения
  qualityScore,  // разложенная оценка
  image,         // canvas с готовой мозаикой
}
```

### Ограничение числа цветов

`selectPaletteSubset` выбирает не первые попавшиеся цвета: делается быстрое
сопоставление, цвета сортируются по востребованности этим снимком, и набор
добирается **пока запаса не хватит на всю сетку**. Поэтому вариант с восемью
цветами всё равно физически собираем — тест проверяет это для 2, 3, 5 и 8
цветов на сетке 32×32.

### Оценка качества

`qualityScore.ts`, никакого рандома — всё считается по пикселям и по
фактическим назначениям:

- **colorSimilarity** — средняя ΔE00 между средним цветом ячейки и цветом
  детали, приведённая к 0..1 по порогу `maxAcceptableDelta`;
- **edgePreservation** — Sobel по исходной сетке и по результату, затем
  `Σ min(источник, результат) / Σ источник`: сколько контура дожило;
- **facePreservation** — та же похожесть цвета, но только по ячейкам глаз, рта,
  контура, лица и волос. Лица нет — берётся общая похожесть, флаг `hasFace`
  честно показывает это;
- **quantityCompliance** — доля деталей, укладывающихся в запас.

Итог — взвешенная сумма (веса в `QUALITY_WEIGHTS`), **умноженная** на
`quantityCompliance`: вариант, который нельзя собрать, не должен побеждать.

Пример реального прогона на портрете 64×64, палитра `portrait`:

```
A Точный цвет:    score 59  (цвет 44, границы 81, лицо 44, запас 100), 12 цветов
B Портрет:        score 66  (цвет 43, границы 82, лицо 73, запас 100), 12 цветов  ← лучший
C Контрастный:    score 50  (цвет 21, границы 74, лицо 50, запас 100), 14 цветов
D Простая сборка: score 43  (цвет 21, границы 80, лицо 21, запас 100),  8 цветов
```

Видно, ради чего всё затевалось: B проигрывает A по чистой цветовой точности,
но выигрывает по лицу (73 против 44) и берёт общий счёт.

Четыре варианта на сетке 64×64 считаются примерно за 2.3 с.

### Интерфейс

Кнопка «Создать 4 варианта» строит карточки: превью, количество деталей,
количество цветов, quality score с разбором по составляющим и отметка о запасе.
Кнопка «Выбрать этот вариант» делает вариант главным результатом — дальше с ним
работают шторка сравнения, зум и скачивание PNG. Лучший по оценке помечается
значком.

Сейчас вариантов двенадцать (G, N, A, B, K, C, D, E, F, H, I, J — см.
`src/config/variants.ts`), они считаются сразу при генерации и показываются
лентой миниатюр под результатом; G только для Classic.

Первым идёт **G «Как в наборе»** — почерк готовых наборов. Сравнение одной
и той же фотографии у нас и у готового набора (64×96, пять тонов) показало
разрыв в числах, а не во вкусе: границ между соседними ячейками 0,36
против наших 0,18, соседей с разницей в два и более тона 11 % против 1 %,
три тона в блоке 4×4 вместо двух. Это нерезкая маска, применённая к сетке,
а не к пикселям (`algorithms/experimental/gridDetail.ts`): яркость ячейки
сравнивается с размытой окрестностью, разница усиливается. Радиус одна
ячейка даёт штрих и светлые ореолы вдоль тёмных черт, радиус четыре — объём
лица. Настройки `detail` / `localContrast` есть у любого варианта; N «Чёткие
черты» — та же пара мягче, для цветных наборов основная. Стенд
`npm run exp:13` считает «почерк» сетки (`experimental/signature.ts`) для
кандидатов и расстояние до подписи набора.

Ориентация картины: наборы M (64×96) собираются и горизонтально — кнопка
«Горизонтально / Вертикально» в шаге кадрирования меняет сетку на 96×64,
кадр на 3:2, деталей столько же; у квадратных наборов кнопки нет. Рядом —
поворот фотографии на 90°.

### Автоподобранный вариант и порядок ленты

Кроме встроенных, в ленту попадают варианты из `src/config/tuned.json` —
их записывает `npm run tune -- --apply` (автоподбор параметров по
бенчмарку, см. CONTINUOUS-IMPROVEMENT.md). Файл проверяется при загрузке:
кривая запись пропускается, значения ограничиваются допустимыми, id не может
совпасть со встроенным. `ALL_VARIANT_PRESETS` = встроенные + подобранные.

Порядок ленты берётся из `src/config/variantRanking.json` — его пишет
`npm run choices -- --apply` по выбору людей, отдельно для Classic/Color и
для фото с лицом/без. Ранжированные варианты идут первыми (первый —
выбор по умолчанию), остальные — в обычном порядке. Пустой файл ничего не
меняет.

## Инструкция по сборке

Алгоритм генерации на этом этапе не менялся: инструкция строится по уже готовой
`MosaicGrid`.

### Блоки

`buildInstructionPlan(grid, { blockSize: 8, palette })` режет мозаику на блоки
слева направо и сверху вниз. 64×64 при блоке 8×8 даёт 64 блока. Каждый блок
хранит `blockId`, `x`, `y`, `width`, `height`, `cells`, а вдобавок — номера
легенды для каждой ячейки, количества по цветам и позицию в решётке блоков.
Если размер не кратен блоку, крайние блоки просто получаются неполными.

Легенда общая на всю мозаику: номера раздаются по убыванию количества, №1 —
самый массовый цвет.

```
1 = Black      900
2 = Blue       700
3 = Hair Dark  700
```

### Build Mode

Шаг «1 / 64», кнопки Previous и Next, полоса прогресса, увеличенная схема блока
с номером в каждой ячейке, количества деталей блока, общая легенда и подсветка
текущего блока на общей картине. Размер блока переключается между 4×4, 8×8 и
16×16 — план пересобирается на лету.

Схема блока рисуется элементами намеренно: там нужны номера и подсказки при
наведении. Сама мозаика по-прежнему живёт в одном canvas.

### PDF

`src/services/` содержит собственный писатель PDF — без внешних библиотек:

- `pdfWriter.ts` — объекты, страницы, xref, трейлер; прямоугольники, линии,
  текст и JPEG через `/DCTDecode`;
- `pdfFont.ts` — разбор TrueType: таблицы `cmap`, `hmtx`, `head`, `hhea`, `OS/2`;
- `pdfGenerator.ts` — сама вёрстка документа.

Структура файла: **обложка → исходная фотография → готовая мозаика → палитра →
статистика → страницы блоков**. На странице блока: заголовок `BLOCK 01`,
координаты, увеличенная схема с номерами, легенда и таблица количеств.

Мозаика 64×64 с блоком 8×8 даёт **69 страниц** и файл примерно на 1.4 МБ.

**Про кириллицу.** Базовые шрифты PDF знают только WinAnsi, поэтому русский
текст в них превращается в мусор. Здесь шрифт встраивается целиком как
CIDFontType2 с кодировкой Identity-H, а к нему прикладывается CMap `ToUnicode` —
без неё текст рисуется правильно, но не копируется и не ищется. Шрифт лежит в
`public/fonts/DejaVuSansMono.ttf` (свободная лицензия); в автономную сборку он
вклеивается base64, поэтому PDF собирается и без сети.

Схемы блоков — векторные прямоугольники, а не картинки: файл остаётся
небольшим, а при печати схема не рассыпается на пиксели. Скриншотов страницы
внутри PDF нет.

### Как это проверено

`npm run test:instruction` собирает документ и **разбирает его обратно** через
pdfjs-dist: считает страницы, читает текст каждой страницы и проверяет, что
кириллица извлекается, что блоки идут по порядку от `BLOCK 01` до последнего и
что на страницах с фотографиями действительно есть XObject-изображение. То же
самое повторяется в браузерном тесте: файл скачивается по-настоящему, потом
открывается и проверяется — 69 страниц, русский текст, порядок блоков.

## Production-обвязка

### Расчёт не блокирует интерфейс

Ядро (`algorithms/mosaicCore.ts`) не знает ни про DOM, ни про canvas — только
пиксели на входе и данные на выходе. Поэтому оно целиком уезжает в Web Worker:
главный поток снимает пиксели (быстро), воркер считает, главный поток рисует.

Замерено в Chromium: генерация 373 мс, при этом самая длинная пауза интерфейса —
96 мс вместо всех 373. Если воркеры недоступны, тот же код считает на месте.

Воркер один на всё время работы страницы (`services/mosaicRunner.ts`): ответы
разводятся по `jobId`, задачи могут ждать очереди. Раньше воркер создавался на
каждую задачу — для одиннадцати вариантов это одиннадцать разборов
полумегабайтного скрипта. Варианты (`variants/variantGenerator.ts`) тоже идут
через воркер. Если воркер не поднимается вовсе (`WorkerUnavailableError`:
скрипт не загрузился, политика безопасности страницы), расчёт один раз
переключается на главный поток и больше воркер не пробует.

**Отмена** — `AbortController`: воркер завершается, ядро между шагами
проверяет флаг и бросает `CancelledError`. Состояние после отмены остаётся
рабочим — следующий запуск поднимает новый воркер.

### Проекты и история

`services/projectStorage.ts` хранит в localStorage только настройки, статистику
и маленькое превью — **фотография не сохраняется**. Есть бюджет байтов,
вытеснение старых записей по LRU, TTL-уборка при старте и обработка
`QuotaExceededError`: при нехватке места старые проекты удаляются, пока
сохранение не пройдёт. Приватный режим Safari, где localStorage бросает
исключение прямо на обращении, отрабатывается отдельной веткой — приложение
работает, просто без истории.

Проект можно переименовать, открыть (настройки применяются, фотографию нужно
выбрать заново) и удалить.

### Ссылка «поделиться»

В ссылку уезжают только настройки: `#p=<base64url>`, меньше 600 символов.
Фотография остаётся у пользователя — это и приватность, и длина URL. Входящая
ссылка **валидируется**: неизвестный размер или режим отклоняются, имя
обрезается, зазор приводится к допустимому диапазону.

### Ограничения и защита

| что | где | как |
| --- | --- | --- |
| Размер файла | `config/limits.ts` | 25 МБ |
| Размер снимка | `lib/fileValidation.ts` | до 8000 px и 40 Мп; больше — уменьшается |
| Подделка формата | `sniffImageFormat` | сигнатура первых байтов, а не расширение |
| Память задачи | `lib/memoryGuard.ts` | оценка до выделения, отказ с понятной ошибкой |
| Частота запросов | `server/rateLimiter.ts` | скользящее окно по IP, 30/мин |
| Параметры запроса | `server/validation.ts` | whitelist размеров, режимов, палитр |

Серверные обработчики вынесены в чистые функции (`server/handlers.ts`), поэтому
проверяются обычными тестами: 200 на корректный запрос, 400 на битый JSON, 422
на `modeId: '../../etc/passwd'`, 429 с `Retry-After` при превышении лимита.

## Продуктовые наборы

Пользователь не выбирает метрику ΔE, вес границ или контраст — он выбирает
набор. Всё остальное определяет конфигурация.

```
Product preset → Processing profile → существующий режим генерации
```

| Набор | Сетка | Картина | Кадр | Палитра | Цветов | Профиль |
| --- | --- | --- | --- | --- | --- | --- |
| Classic S | 64×64 | 51×51 см | 1:1 | classic | 5 | portrait-balanced |
| Classic M | 64×96 | 51×76 см | 2:3 | classic | 5 | portrait-balanced |
| Classic L | 96×96 | 76×76 см | 1:1 | classic | 5 | portrait-balanced |
| Color S | 64×64 | 51×51 см | 1:1 | color | 6 + основа | color-portrait |
| Color M | 64×96 | 51×76 см | 2:3 | color | 6 + основа | color-portrait |

Наборы описаны в `src/config/productPresets.ts`. Интерфейс берёт список
оттуда: новый набор добавляется одной записью, без правок приложения.

**Профили** (`src/config/processingProfiles.ts`) ничего не вычисляют — они
называют по-продуктовому набор существующих настроек и указывают, какой режим
(Standard / Portrait / High Contrast / Artistic) лежит под ним. Сами режимы не
изменены.

**Запас деталей** задаёт пресет, а не палитра: в `palettes.json` лежит
заглушка, а `buildPresetPalette` распределяет `availablePieces` набора между
цветами. Коэффициент `PIECE_GENEROSITY` = 1.55 к числу ячеек — иначе перекос по
одному цвету делал бы картину несобираемой.

**Цвета названы рабочими именами** (`Classic 1–5`, `Color A–F`, `Base`).
Официальных кодов чужих производителей в конфигурации нет, и тест это
проверяет.

### Шаги интерфейса

1. Набор → 2. Фото → 3. Кадрирование → 4. Генерация → 5. Результат.

Пропорции кадра берутся из набора автоматически: 1:1 или 2:3. Несовместимое
соотношение выбрать нельзя.

### Advanced

Все технические настройки сохранены в свёрнутом разделе «Advanced · для
тестирования алгоритма»: режим, размер, палитра (включая тестовые — они
помечены `· test`), метрика, лимиты и debug-состояние `feasible / satisfied`.
Пока не включён переключатель «Ручные настройки», параметры берутся из набора.

Палитры «Серая (4)», «Базовая (12)» и «Портретная (14)» никуда не удалены —
они просто не показываются покупателю.

### Статус набора

Вместо технического `infeasible` покупатель видит фразу: «Этот набор подходит
для выбранной фотографии» или «Для этой фотографии требуется слишком много
деталей одного цвета» с перечислением цветов. Техническое состояние осталось в
Advanced.
