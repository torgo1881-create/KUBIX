# Как алгоритм улучшается постоянно

До сих пор каждое улучшение проверялось вручную, и каждое второе что-то
ломало незаметно: параметр силы дизеринга не работал, детектор проваливался
в квадратном кадре, «серый мир» ломал детекцию. Ниже — контур, который
ловит такое автоматически.

## Три контура обратной связи

### 1. Регрессионный бенчмарк — перед каждым изменением

```
python3 tools/prepare-benchmark.py <папка с фото>   # один раз
npm run bench                                       # сравнить с эталоном
npm run bench -- --update                           # принять новый эталон
```

Гоняет четыре опорных варианта по всем кадрам и сравнивает с
`benchmark/baseline.json`:

- **детекция** — сколько кадров с уверенно найденным лицом; потеря хотя бы
  одного лица называется поимённо;
- **узнаваемость** каждого варианта — падение больше 0,01 считается регрессией;
- **запас деталей** — любое нарушение блокирует.

Скрипт возвращает ненулевой код при регрессии, поэтому его можно поставить
в pre-commit или CI. Фотографии в репозиторий не попадают — только кадры в
`benchmark/frames`, и те в `.gitignore`.

Правило: **нет изменения в алгоритме без прогона бенчмарка**. Улучшение по
метрике на одном фото не считается, пока не подтверждено на всём наборе.

### 2. Выбор пользователей — из интерфейса

Каждый выбор варианта пишется в localStorage: id варианта, набор, найдено
ли лицо, оценка. Никаких фотографий. В Advanced — кнопка «Экспорт выборов
вариантов», отдаёт JSON со сводкой.

Зачем: метрики говорят, что лучше по числам; выбор говорит, что лучше
глазами. Расхождение между ними — самый ценный сигнал. Если вариант «Как на
фото» лидирует по метрике, а люди выбирают «Светлое лицо + глаза», значит
метрику надо калибровать, а не вариант.

Что делать с данными раз в месяц:
- вариант, который выбирают реже 3 % — убрать или переделать;
- вариант-лидер — сделать первым в ленте;
- если лидер меняется в зависимости от `faces: 0/1` — разветвить порядок.

Инструмент для этого — `npm run choices`: принимает файлы экспорта (можно
папку), склеивает их без дублей и считает решения, а не клики: внутри одного
сеанса генерации человек щёлкает по ленте и сравнивает, решением считается
последний клик. Отчёт показывает победителей всего, по наборам и по группам
«тип набора × есть ли лицо», долю сеансов, где сравнивали, среднюю позицию
выбранного в ленте (виден ли сдвиг «берут первое») и чем настройки
победителей отличаются от среднего — например, что победители контрастнее.

```
npm run choices -- exports/*.json          # отчёт
npm run choices -- exports/ --apply        # записать порядок ленты
```

С `--apply` порядок победителей пишется в `src/config/variantRanking.json`
— отдельно для Classic и Color, с лицом и без, и только для групп, где
решений не меньше порога (`--min`, по умолчанию 10: на пяти кликах порядок
менять нельзя). Генератор ставит эти варианты первыми, первый становится
выбором по умолчанию. Настройки вариантов это не меняет — только порядок.

### 3. Эталоны от конкурентов — при появлении

Единственный объективный ориентир, который сдвинул алгоритм за всё время, —
PDF Mozabrick с распределением деталей. Именно из него вышел тональный
баланс. Каждый новый эталон (их результат на нашем же фото) стоит:

- прогнать наше фото через все варианты;
- измерить распределение тонов, рябь, рельеф;
- сравнить с эталоном тем же скриптом, что в `tools/experiment-12.mjs`;
- снять «почерк» сетки (`src/algorithms/experimental/signature.ts`): границы
  между соседями, скачки на два тона, одиночные ячейки, тонов в блоке 4×4.
  Именно так в октябре нашёлся главный разрыв с готовыми наборами — не в
  тоне, а в локальном контрасте по ячейкам; стенд `npm run exp:13`
  сравнивает кандидатов с подписью набора `KIT_SIGNATURE`.

### 4. Автоподбор параметров — по бенчмарку

```
npm run tune                                 # от варианта I, все параметры
npm run tune -- --variant B --params contrast,dithering
npm run tune -- --category classic --frames 24 --budget 60
npm run tune -- --apply                      # записать как вариант «Автоподбор»
```

Берёт настройки встроенного варианта как старт и ходит покоординатным
спуском: по одному параметру, шаг вниз и шаг вверх, принимается только
шаг, который улучшает среднюю узнаваемость и не нарушает ограничения —
запас деталей на каждом кадре и рябь не выше стартовой плюс 2 %. Метрика
та же, что в `npm run bench`, поэтому результат согласован со шлюзом.
Поиск можно вести на подвыборке кадров (`--frames`), но найденное всегда
проверяется на всех: не подтвердилось — не записывается. Считает в
несколько потоков (`--jobs`, по умолчанию все ядра); отчёт с каждым
принятым шагом — в `benchmark/tune/`.

Что это даёт и чего не даёт. Подбор улучшает ровно то, что измеряет
метрика. Первый же полный прогон это показал: метрика меряет верность
исходному снимку (SSIM и ΔE считаются к сетке с оригинала), поэтому она
выключила подъём тёмного лица и растяжение гистограммы — то, ради чего
вариант «Светлое лицо» существует, — и получила +0,01. По той же причине
она любит контраст пониже (меньше ряби и ΔE). Поэтому тональные
переключатели (`faceExposure`, `levels`) по умолчанию не подбираются —
только если назвать их в `--params`; их судьбу решает выбор людей. А сам
результат с `--apply` попадает в ленту **отдельным вариантом**
«Автоподбор» (`src/config/tuned.json`), а не заменяет встроенные:
выигрывает ли он у ручных настроек, покажет сводка выборов. Если
выигрывает — его настройки можно сделать основой встроенного варианта;
если нет — это сигнал калибровать метрику, и это тоже результат.

Как замыкается круг: бенчмарк → `tune` → вариант в ленте → выбор людей →
`choices --apply` → порядок ленты и повод скорректировать метрику →
снова `tune`. Ни один шаг не меняет production сам: между ними стоят
`npm run bench` и тесты.

Следующий шаг по метрике, который напрашивается из первого прогона:
сделать её нечувствительной к намеренному тону — считать структурную
часть SSIM без слагаемого яркости и добавить целевое распределение тонов
из эталона набора (как в `tools/experiment-12.mjs`). Тогда автоподбор
сможет судить и о «Светлом лице», а не только о резкости и ряби.

## Чего не делать

- Не доверять автоподбору без выбора людей: он оптимизирует метрику, а не
  восприятие. Вариант «Автоподбор» живёт в ленте рядом со встроенными ровно
  для того, чтобы это проверялось.
- Не менять production по одному фото. Снимок из жалобы — повод найти класс
  проблемы (как сдвиг цвета при свете экрана), а не подкрутить параметр.
- Не доверять одной метрике. `recognitionScore` — наша конструкция; она уже
  один раз ошибалась в оценке дизеринга.
- Не расширять пороги детектора «чтобы находило больше»: ослабление
  применяется вторым проходом, только когда строгий провалился, — так
  нормальные снимки не меняются.

## Чему научил последний случай

Один снимок при свете экрана вскрыл три разных дефекта, и каждый был бы
незаметен без измерения. Первое решение (баланс белого «серый мир»)
выглядело очевидным и оказалось вредным — оно ломало тёплые снимки.
Правильное (якорь по коже) появилось только после того, как были измерены
Cb и Cr на конкретных пикселях. Порядок работы, который себя оправдал:

1. воспроизвести на кадре и **измерить** причину, а не предположить;
2. проверить кандидата на всём наборе, включая те снимки, которым он не нужен;
3. прогнать `npm run bench` — до и после;
4. только потом менять production.
